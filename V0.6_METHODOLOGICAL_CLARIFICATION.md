# v0.6-Prospective — Methodological Clarification

**Status: a new, prospective methodological decision made during this revision. It is explicitly NOT part of the frozen, owner-ruled v0.4 codebook (`CODEBOOK_RULE_SPECIFICATION.csv`, rules R01–R18), and it is not claimed to have been part of any pre-registered or historical methodology. It must be disclosed as such wherever it is cited in the manuscript.**

## The confirmed defect in the original (v0.3/v0.5) engine

`run/scripts/x3_build_units_v0.3.py`, function `judge_dimension()` (SHA-256 `e888ab0a22f66c1ba99029a3f48643f37161b4fea00f931ba1a53f46e3fb9409`, unmodified), handles missingness statuses (`NA`, `NR`, `UNA`) asymmetrically:

- If **either** side's status is `UNA`, the function already short-circuits: both `UNA` → `UNA-GENUINE`; one `UNA` → `AMBIGUOUS` ("cannot confirm a real difference against an inaccessible value").
- If **both** sides' status are in `{NA, NR}`, the function short-circuits: same status → `{status}-GENUINE`; different (`NA` vs `NR`) → `AMBIGUOUS`.
- **If exactly one side's status is `NA` or `NR` and the other side has a real value (`REP`/`PART`), no guard fires.** Execution falls through to the generic canonicalization-and-compare path.

In that generic path, several of the per-field canonicalization functions (`run/scripts/x3_canon_v0.3.py`) convert a missingness *status* into an ordinary literal tag or leave the free-text "explanation" of that missingness exposed to keyword/regex matching:

- `canon_f03`, `canon_f06`: `if status == 'NA': return frozenset(['NA'])` — a literal string tag, compared by set-disjointness against the other side's real tag. Disjoint by construction → spurious `GENUINE`.
- `canon_f16`: identical pattern for `status == 'NR'`.
- `annot_range()` (used in F09's bespoke branch): extracts any 1–2 digit number via regex from free text, with no awareness of citation brackets — e.g. "inherited from [19],[20]" is misread as an annotator-count range (19,20).
- `canon_f02`, `canon_f08`: keyword/percentage regexes can match incidentally on numbers or phrases inside NA/NR-*explanatory* prose (e.g. a sentence stating "15% appears only as [an unrelated parameter], not as the summary-length budget actually used" yields a spurious `pct:15.0` tag).

All of the above were confirmed by direct, live execution of the unmodified original function against real extraction records (see Stage 1E/1F audit trail), not inferred from documentation. Sample verifications:
- `judge_dimension('F06', {status:'NA',...}, ..., {status:'PART', value:'KTS used'...}, ...)` → `GENUINE` (confirmed).
- `judge_dimension('F09', ..., value='Not described; inherited from [19],[20]', ..., value='15-18 annotators'...)` → `GENUINE`, "annotator-count ranges do not overlap ((19, 20) vs (15, 18))" (confirmed — the (19,20) range is drawn entirely from citation numbers, not an annotator count).

## The prospective rule adopted for v0.6

Generalize the **existing** one-sided `UNA` guard to also cover one-sided `NA` and one-sided `NR`, with the same destination (`AMBIGUOUS`) the engine already uses for one-sided `UNA`. Symmetric cases (both sides the same status) are **unchanged** and keep their existing `NA-GENUINE` / `NR-GENUINE` / `UNA-GENUINE` treatment and bucket mapping (R07).

This is the smallest change that:
1. Is derived from a demonstrable code defect, not an unexplained bulk reclassification.
2. Reuses a decision pattern the engine's own original author already applied to `UNA` — it is not a new invented category.
3. Does not touch any field's canonicalization vocabulary, symmetric-missingness handling, or any other verdict path.

Implementation: a non-invasive wrapper (`run/x3_full_analysis_v0.6_prospective.py`) around the unmodified, hash-verified original function. **The original `x3_build_units_v0.3.py` and `x3_canon_v0.3.py` were never edited** — the preserved copies in `run/scripts/` are byte-identical to the project's originals (hashes verified against `MASTER_FORENSIC_AUDIT_REPORT.md`'s own cited hashes and against the Stage 1B baseline reproduction).

## What this does NOT resolve

- **464 of Phase 6.2's 8,406 changed cells (all field F09, mostly `GENUINE`→`AMBIGUOUS`) are not covered by this rule.** They are not one-sided-missingness cases by the criterion used here (both sides' statuses were not in `{NA, NR, UNA}` vs. real-value combinations). No explanation for these 464 has been verified. They are listed individually, with their v0.5/v0.6/Phase-6.2 verdicts, in `V0.6_CHANGE_REGISTER.csv` with status `phase6.2_only -- UNRESOLVED`. **This package does not adopt, explain, or guess at a justification for them.**
- Whether `NA` and `NR` should, in a future codebook revision, actually be resolved differently from each other in the one-sided case (the frozen codebook already treats them differently when symmetric: `NA-GENUINE`→SAME vs. `NR-GENUINE`→UNASSESSABLE) is a genuine open question this package does not settle. v0.6-prospective treats both identically (→ `AMBIGUOUS`), matching the engine's existing `UNA` precedent rather than inventing a split. This choice should be stated explicitly in the manuscript's methodology section as the specific clarification made, so a reviewer can evaluate it on its own terms.
